# Phase 6 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** two UI surfaces, plus one degraded state — (1) the terms block added to the existing registration form at `/registro`, (2) the new mandatory acceptance gate at `/[slug]/admin/aceitar-termos`, (3) the fail-closed variant of `/registro` when no terms version exists. Everything else in Phase 6 is schema, service, guard and endpoint work with no visual output (the publication endpoint is API-only by D-04 — **there is no superadmin screen in this phase**).

**Prime directive:** this phase introduces **zero** new visual language. Both surfaces are assembled from markup that already exists in this repository: the registration/login/blocked card shell, the `INPUT_CLASS` form rhythm of `register-form.tsx`, the `<details>/<summary>` pattern of `collapsible-section.tsx`, the single inline-error block used by `login-form.tsx` / `register-form.tsx` / `bloqueado-card.tsx`, and the `Sair da conta` secondary button of `bloqueado-card.tsx`. Every token below was extracted from existing code, not invented.

**Deliberate divergence from Phase 4, stated up front:** the acceptance gate is **not amber**. Phase 4 established amber as the payment/suspension language (grace banner → blocked screen, "the same warning colour escalating from a strip to a full screen"). Pending terms is not a payment problem, cannot be resolved by paying, and carries no loss of service. Reusing amber here would teach the user that a document to read and an overdue invoice are the same event. The gate uses the neutral slate ramp. See §Color.

### Modal decision (D-11 → Claude's Discretion, decided here)

D-11 locks *"checkbox obrigatório + um link ou modal que mostra o texto completo … sem sair da tela"*, and explicitly rules out inline body text and a separate route. The mechanism was left to discretion. **Decision: native `<details>/<summary>` disclosure, not a modal.**

| Why | Detail |
|-----|--------|
| The project has no modal | Confirmed absent twice (Phase 4 §Ausências confirmadas, and again in `06-RESEARCH.md`). `grep '<dialog\|role="dialog"\|aria-modal'` over `app/` returns **zero** hits. |
| The project already has this exact disclosure | `app/[slug]/admin/(protected)/_components/collapsible-section.tsx` — 15 lines, `<details>` + styled `<summary>`, zero JS. The **pattern** is reused; the **file is not imported** (it lives inside `(protected)`, a tree `/registro` must not reach into). |
| A modal here is a system, not a component | A correct modal needs focus trap, scroll lock, `Escape`, return-focus and a portal. Establishing all of that to reveal one block of text — on a page that is otherwise a plain form — is inventing a design system inside a phase forbidden from inventing one. |
| It satisfies D-11 literally | The text is revealed in place, without leaving the registration screen and without a separate route. |

`<details>` also degrades perfectly with JS disabled, which matters on the one screen in the product that has no session yet.

## Spacing Scale

Base unit 4px (Tailwind 4 default `--spacing`). Declared values (all multiples of 4):

| Token | Value | Tailwind | Usage in this phase |
|-------|-------|----------|---------------------|
| xs | 4px | `1` / `mt-1` | Version meta line under the gate heading |
| sm | 8px | `2` / `gap-2`, `mt-2` | Icon-to-text gap inside the inline error block; heading-to-body gap |
| md | 12px | `3` / `gap-3`, `mt-3`, `py-3`, `px-3` | Checkbox-to-label gap; button vertical padding; button stack gap |
| lg | 16px | `4` / `p-4`, `mt-4`, `space-y-4` | Terms-text box padding; shell padding; existing form field rhythm |
| xl | 24px | `6` / `mt-6` | Accept-button separation from the terms text |
| 2xl | 32px | `8` / `p-8` | Gate card interior padding (mirrors registro and bloqueado) |
| 3xl | 48px | `12` | Reserved — not used by this phase |

**Scroll-region heights** (both multiples of 4, both binding):

| Surface | Class | Value |
|---------|-------|-------|
| Gate screen terms box | `max-h-72` | 288px |
| Registration disclosure terms box | `max-h-64` | 256px |

The registration box is shorter on purpose: it sits inside an already-tall form and must not push `Criar minha loja` off-screen when opened.

**Exceptions:** two, both pre-existing and inherited, neither introduced by this phase:

1. `app/registro/_components/register-form.tsx` uses `py-2.5` (10px) and `mb-1.5` (6px) on its inputs and labels (`INPUT_CLASS`, line 9). New markup added to that file **matches the surrounding `space-y-4` rhythm but does not adopt `py-2.5` on any interactive control** — see touch target below.
2. `app/registro/page.tsx` uses `h-2` (8px — a multiple of 4, fine) for the gradient bar. Retained.

**New markup in this phase must not introduce any non-multiple-of-4 spacing value.** In particular: **do not use `mt-0.5` (2px) to optically align the checkbox.** The checkbox is sized `h-5 w-5` (20px) against a `text-sm/[1.5]` line box (21px), which aligns within 1px at `items-start` with no margin at all.

**Minimum touch target — 44px, verified per control:**

| Control | Composition | Height |
|---------|-------------|--------|
| `Aceitar e continuar` | `py-3` (24px) + `text-sm` line box (20px) | 44px ✅ |
| `Sair da conta` | `py-3` (24px) + `text-sm` line box (20px) | 44px ✅ |
| `<summary>` disclosure row | `py-3` (24px) + `text-sm/[1.5]` line box (21px) | 45px ✅ |
| Checkbox `<label>` row | `py-3` (24px) + `text-sm/[1.5]` line box (21px) | 45px ✅ |

`py-2.5` yields 40px and is **forbidden on every interactive control introduced by this phase** — including the `<summary>`, which is why the new disclosure deviates from `collapsible-section.tsx:9` (that component's `py-2.5` predates this rule and is not edited here).

## Typography

Three sizes, two weights. Line heights are declared as ratios and implemented with Tailwind 4's line-height modifier (`text-sm/[1.5]`).

| Role | Size | Weight | Line Height | Tailwind | Where |
|------|------|--------|-------------|----------|-------|
| Body | 14px | 400 (`font-normal`) | 1.5 | `text-sm/[1.5]` | **The terms text itself (both surfaces)**, gate explanation, checkbox label, disclosure summary |
| Label | 12px | 600 (`font-semibold`) | 1.33 | `text-xs font-semibold` | Existing form field labels (unchanged) |
| Meta | 12px | 400 (`font-normal`) | 1.33 | `text-xs` | Version line (`Versão 3 · publicada em 02/09/2026`); inline error text |
| Heading | 20px | 600 (`font-semibold`) | 1.2 | `text-xl/[1.2]` | Gate screen `<h1>` |
| Display | — | — | — | — | **Not used in this phase** |

**Button labels** are `text-sm font-semibold` (14px / 600) — matching `login-form.tsx:71`, `register-form.tsx:126` and `bloqueado-card.tsx:106` exactly.

### Binding rule: the terms text renders at 14px, never 12px

`06-RESEARCH.md` §"Disclosure do termo no registro" sketches the registration disclosure body at `text-xs` (12px). **This contract overrides that to `text-sm/[1.5]` (14px / 1.5) on both surfaces.** The terms are the one piece of copy in this product the user is legally being asked to have read; setting them two steps below body size on the registration screen — while the field labels around them sit at the same 12px — signals "boilerplate, skip it" and is the exact dark-pattern shape a consent record exists to disprove. 14px at 1.5 line-height is the project's body setting and is what a document meant to be read gets. The research snippet's `whitespace-pre-wrap` / `overflow-y-auto` / `max-h-*` structure is otherwise adopted verbatim.

**Legacy carve-out (one, documented):** `app/registro/page.tsx:30` renders its `<h1>` at `text-xl font-bold` (700). This phase does not touch that page's heading. **No new markup in this phase may use weight 500 or 700.**

**Rationale for 400+600:** the codebase histogram is `font-semibold` 126 × `font-bold` 45 × `font-medium` 28 — semibold is the established emphasis weight. Body copy in the codebase carries no weight class, i.e. 400.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f8fafc` (`slate-50`) | Page background of both full-screen surfaces; fill of the terms scroll box |
| Secondary (30%) | `#ffffff` (`white`) | The card on both surfaces |
| Accent (10%) | Gate: tenant `empresa.primaryColor`, fallback `#18181b`. Registro: `#18181b` fixed | See reserved list below |
| Neutral status (semantic) | `#f1f5f9` (`slate-100`) tile, `#475569` (`slate-600`) glyph | Gate screen status tile **only** |
| Error (semantic) | red ramp — surface `#fef2f2` (`red-50`), border `#fecaca` (`red-200`), icon `#ef4444` (`red-500`), text `#dc2626` (`red-600`) | Inline error block on both surfaces |
| Warning (amber) | **forbidden in this phase** | Amber belongs to the payment/suspension language established in Phase 4. See below. |
| Destructive | **not used** | This phase has no destructive action — see Copywriting Contract |

**Text colors** (inherited, unchanged): `slate-800` primary text, `slate-700` terms body, `slate-600` form labels and checkbox label, `slate-500` secondary/body, `slate-200` control borders, `slate-100` card borders.

### Accent reserved for — explicit list

Accent (tenant `primaryColor` on the gate; `#18181b` on registro) may be applied to **exactly these four things** in this phase:

1. The `background` of the gate screen's `Aceitar e continuar` button.
2. The `--tw-ring-color` focus ring of that same button.
3. The 8px gradient bar at the top of the gate card (`linear-gradient(90deg, primaryColor, accentColor)`), mirroring `bloqueado-card.tsx:40-45`.
4. The native checkbox's `accent-color` on the registration form (`accent-slate-800`, matching the `bg-slate-800` submit button directly below it).

**Accent is explicitly NOT used for:** the `Sair da conta` button, the `<summary>` disclosure row, the terms scroll box border or fill, the status tile, body text, or the version meta line.

### Why the status tile is slate, not amber

Phase 4 spent its colour budget teaching one association: **amber = your payment situation**. It appears on the grace banner and escalates to the blocked screen's tile, and `04-UI-SPEC.md` states that escalation as intent. Pending terms is a different event with a different remedy — nothing is overdue, nothing is suspended, and paying does not clear it (which is exactly why `06-RESEARCH.md` §Achado Crítico 2 specifies `403`, not `402`, on the API mirror of this gate). A slate tile with a document glyph reads as procedural, which is what it is. Reusing amber would spend a learned signal on the wrong event and, for a user who is *also* in carência, would put two identical amber screens in one session meaning two unrelated things.

**No amber utility class may appear in any file created or edited by this phase.** This is a grep-checkable rule.

### Registration accent is fixed, not tenant

`/registro` is pre-tenant — no `Empresa` row exists yet, so there is no `primaryColor` to read. The page's existing gradient is hardcoded `linear-gradient(90deg, #18181b, #f59e0b)` (`registro/page.tsx:21`); it is **not** edited. The checkbox accent is `slate-800` (`#1e293b`), tied to the submit button beneath it rather than to the gradient's amber terminus — amber on a checkbox would be the sole amber interactive control in the product and would read as a warning about the thing being agreed to.

**Inherited contrast risk (out of scope, do not "fix" here):** a tenant that picks a pale `primaryColor` already gets white-on-pale text on the login and blocked-screen buttons today. The gate reproduces that existing pattern. Validating tenant colour contrast is a separate concern with a separate blast radius.

Tone, inherited from `04-UI-SPEC.md` and the existing register (`"Sessão inválida."` / `"Entrar no painel"` / `"Criando conta..."`): direct Portuguese, second person, no exclamation marks, no apology, no legal jargon, no "por favor".

| Primary CTA (registro) | **`Criar minha loja` — UNCHANGED.** Pending: `Criando conta...` — UNCHANGED. See the lock below. |

| Disclosure trigger (registro) | `Ler os Termos de Uso (versão {n})` |

| Empty state body | See below — none. |
| Error state | Four strings, tabulated below |

The existing logout controls (`admin-nav.tsx:114`, `simples-top-bar.tsx:45`, `bloqueado-card.tsx:103-110`) use no confirmation and no red tint; adding either here would be inconsistent and would misrepresent the action. Do **not** wire `ConfirmSubmitButton` to it. |

### Locked string: `Criar minha loja` must not change

`06-RESEARCH.md` §Pitfall 6 verifies that **all 9 e2e spec files** register through the `/registro` UI, with **13 occurrences of the `Criar minha loja` locator**, and that each spec carries its own private registration helper (there is no shared one in `e2e/helpers.ts`). Renaming that button — or changing its pending label — turns a checkbox regression into 9 simultaneous timeout failures pointing at the wrong cause. The registration CTA copy is frozen for this phase.

### Gate screen copy (TERM-04)

Heading (`<h1>`): **`Termos de Uso`**

Body: **`Publicamos uma versão dos termos que você ainda não aceitou. Leia o texto abaixo e aceite para voltar ao painel.`**

**One string for both populations.** This gate fires for two different users: someone whose previous acceptance is now outdated, and — on the first deploy — every existing user in the database, none of whom has ever accepted anything (`06-RESEARCH.md` §Runtime State Inventory: "100% dos usuários existentes entram em `termosPendentes = true`"). The sentence above is true for both. **The executor must not branch the copy on whether a prior acceptance exists**, for the same reason Phase 4 forbade branching `BLOQUEADO` vs `CANCELADO`: a second string is a second thing to keep true, bought with no user benefit.

`voltar ao painel` is a factual claim backed by D-10 (the Server Action redirects to `/{slug}/admin`). Do not promise the specific page the user was heading to — `06-RESEARCH.md` §Máquina de Estados rejects `?next=` as an open-redirect vector.

### Error strings

| # | Condition | Copy | Surface |
|---|-----------|------|---------|
| E1 | TOCTOU — terms were republished between render and submit (`termoId` ≠ current) | `Os termos foram atualizados enquanto você lia. Leia a nova versão e aceite novamente.` | Gate |
| E2 | Same, during registration | `Os termos foram atualizados. Leia a nova versão e aceite novamente para criar sua conta.` | Registro |
| E3 | Checkbox absent from the payload (server-side half of D-11) | `É preciso aceitar os Termos de Uso para criar a conta.` | Registro |
| E4 | No terms version exists at all (fail-closed registration path) | `Não foi possível abrir o cadastro agora. Tente novamente em alguns instantes.` | Registro (degraded) |

E1 and E2 are the user-visible face of `06-RESEARCH.md` §Pitfall 4 and **must be accompanied by a re-render showing the new text** — an error that says "read the new version" while still displaying the old one is worse than no error. E4 is deliberately generic: per CLAUDE.md §Error Handling the real cause ("nenhum termo publicado") goes to `console.error` only. E3 is specific because the user can act on it directly.

### Why there is no empty state

Neither surface can legitimately render "no terms available":

- **Gate:** `termosPendentes` is `false` when no terms exist (`06-RESEARCH.md` §"Assimetria deliberada" — the gate fails **open** so a missing document cannot take down every tenant at once). The page's own symmetric guard then redirects to `/{slug}/admin`. The gate is unreachable without a terms row.
- **Registro:** v1 is seeded by migration, so every environment that has run `prisma migrate deploy` — including CI — has one. The null branch exists only as a fail-closed backstop.

**Building an empty state on either surface is a contract violation, not a nicety.** A friendly `Nenhum termo publicado` screen on the gate is an invitation to make the gate fail open in a *second* place, and on registro it is a form that looks usable and cannot submit. See the degraded state in §Surface Inventory instead.

## Component Contracts

### 1. Registration terms block (edit to `RegisterForm`)

**New props** on the existing `RegisterForm`:

```ts
{
  action: (state: RegisterState, formData: FormData) => Promise<RegisterState>; // existing
  termo: { id: string; versao: number; conteudo: string };                       // NEW, required
}
```

`page.tsx` reads `termoVigente()` and passes it down. The prop is **required, not optional** — the null case is handled by the page (Surface 3), so this component never has to render a half-state.

**Placement:** immediately **after** the `ModoInterfacePicker` block and **before** the `{state.error && ...}` block, so a server-side rejection (E2/E3) appears directly above the submit button where it already does today. The block participates in the form's existing `space-y-4` rhythm.

**Structure (class strings binding):**

```
<div>
  <details class="rounded-xl border border-slate-200 bg-slate-50/60 px-3">
    <summary class="cursor-pointer select-none py-3 text-sm/[1.5] font-medium text-slate-600">
      Ler os Termos de Uso (versão {termo.versao})
    </summary>
    <div
      role="region"
      aria-label="Texto dos Termos de Uso"
      tabindex="0"
      class="mb-3 max-h-64 overflow-y-auto whitespace-pre-wrap rounded-lg border border-slate-200
             bg-white p-4 text-sm/[1.5] text-slate-700"
    >
      {termo.conteudo}
    </div>
  </details>

  <label class="flex cursor-pointer items-start gap-3 py-3 text-sm/[1.5] text-slate-600">
    <input type="checkbox" name="aceiteTermos" required
           class="h-5 w-5 shrink-0 rounded border-slate-300 accent-slate-800" />
    <span>Li e aceito os <span class="font-semibold text-slate-800">Termos de Uso</span></span>
  </label>

  <input type="hidden" name="termoId" value={termo.id} />
</div>
```

**Binding rules:**
- `required` on the checkbox is the client half of D-11; the Server Action refusing without it is the server half. **Both, always** (`app/registro/actions.ts` already applies this discipline to email/senha).
- `name="aceiteTermos"` and `name="termoId"` are the contract with `actions.ts`. `formData.get("aceiteTermos") === "on"` is the native checkbox value.
- The hidden `termoId` is **client-controlled data**. The server compares it for **equality against its own current version** and refuses on mismatch (E2) — it never trusts it as a selector. `06-RESEARCH.md` §Pitfall 4.
- `font-medium` (500) on the `<summary>` is **not** permitted — the table above specifies `font-medium` in `collapsible-section.tsx`, but this phase's weight contract is 400/600 only. **Use `font-semibold`.** (Corrected here deliberately; `collapsible-section.tsx` itself is not edited.)
- The `<details>` stays **closed by default**. Open-by-default would make the terms an inline wall of text, which D-11 explicitly rejected.
- The scroll box carries `role="region"` + `aria-label` + `tabindex="0"` so keyboard users can reach and scroll it — a scrollable container with no focusable content is otherwise unreachable without a mouse.
- **No `<dialog>`, no portal, no `useState` for the disclosure.** The native `<details>` toggle adds no React state to a component that already has one `useState` for the mode picker.

### 2. Acceptance gate — `AceiteCard`

**Props (server-computed; the component makes no decisions):**

```ts
{
  primaryColor: string;                      // empresa.primaryColor ?? "#18181b"
  accentColor: string;                       // empresa.accentColor  ?? "#3f3f46"
  termo: { id: string; versao: number; conteudo: string; publicadoEm: Date };
  erro: boolean;                             // E1 — terms changed under the user
  aceitarAction: (formData: FormData) => Promise<void>;
  logoutAction: () => Promise<void>;
}
```

Same discipline as `BloqueadoCard`: the props are **decisions already taken**, not raw state. The component contains no `new Date()`, no status comparison, and no branch on whether a prior acceptance existed.

**Structure (shell mirrors `bloqueado-card.tsx` 1:1 so the user recognises the surface):**

```

      <div class="p-8">
        <div class="mx-auto mb-4 flex h-16 w-16 items-center justify-center rounded-2xl bg-slate-100">
          <svg class="h-8 w-8 text-slate-600" />           ← document-text glyph, NOT a padlock
        </div>

        <h1 class="text-center text-xl/[1.2] font-semibold text-slate-800">Termos de Uso</h1>
        <p class="mt-1 text-center text-xs text-slate-500">
          Versão {versao} · publicada em {dd/mm/aaaa}
        </p>
        <p class="mt-2 text-center text-sm/[1.5] text-slate-500">{body copy}</p>

        <div
          role="region" aria-label="Texto dos Termos de Uso" tabindex="0"
          class="mt-4 max-h-72 overflow-y-auto whitespace-pre-wrap rounded-xl border border-slate-200
                 bg-slate-50 p-4 text-sm/[1.5] text-slate-700"

          {termo.conteudo}

          </button>
        </form>
      </div>
    </div>
  </div>
</div>
```

**Binding rules:**
- The `Sair da conta` block is **copied verbatim from `bloqueado-card.tsx:103-110`**, including its comment about not being destructive. `logoutAction` is the **existing** `logout` Server Action (`app/[slug]/admin/_lib/auth-actions.ts:50-53`), bound as `logout.bind(null, slug)`. Do not write a new one — it does not call `requireAdminSession`, so it works from a gated session. This is the "never trapped" guarantee of success criterion #4.
- The tile glyph is a **document**, not a padlock. The padlock is Phase 4's vocabulary for *locked out*; this user is not locked out of anything they have paid for.
- The full terms text is rendered as a **React text node** — automatic escaping. **`dangerouslySetInnerHTML` is forbidden in this phase**, on either surface. D-05 makes the content plain text precisely to remove that surface.
- `publicadoEm` is formatted **on the server** and passed as a string, or formatted with the project's existing date helper. **`new Date()` must never appear inside this component** — same rule Phase 4 set for `AvisoCarencia`, same reason (testable without fake timers).
- No "scroll to bottom before you can accept" gating. It is not required by TERM-01/TERM-04, it breaks on short terms and on zoomed viewports, and it is the kind of friction that gets worked around rather than read.

### 3. `AceitarButton` — gate primary CTA

Client component (`"use client"`), consumes `useFormStatus()` from `react-dom` — **not** `useActionState`, because the action returns `void` and terminates in `redirect()`, so there is no state to render back. This mirrors `PagarButton` exactly (`app/[slug]/admin/_components/pagar-button.tsx`).

```
class: "w-full rounded-xl py-3 text-sm font-semibold text-white shadow-md transition-all
        hover:shadow-lg active:scale-[0.98] disabled:opacity-60 focus:ring-2"
style: { backgroundColor: primaryColor, "--tw-ring-color": primaryColor }
label: "Aceitar e continuar"  →  "Registrando aceite..." while pending
disabled: pending
```

The class string is **character-identical to `PagarButton`'s `bloqueado` variant**, which is itself identical to `login-form.tsx:71` plus `focus:ring-2`. Deliberate reuse, not coincidence.

**The action it submits to must authorise itself.** It lives outside `(protected)`, so no guard covers it: it calls `getVerifiedSession()`, checks the slug, and derives `usuarioId` **from the session, never from the form** (`06-RESEARCH.md` §Pitfall 8). That is a plan concern, restated here because it constrains the markup: **no `usuarioId` hidden input may exist in this form.**

### 4. `InlineError` — shared error block

Reuse the exact block already in `login-form.tsx:50-66`, `register-form.tsx:104-121` and `bloqueado-card.tsx:76-93`:

```
<div class="mt-4 flex items-center gap-2 rounded-xl border border-red-200 bg-red-50 px-3 py-2.5">
  <svg class="h-4 w-4 shrink-0 text-red-500" />     ← exclamation circle
  <span class="text-xs text-red-600">{error copy}</span>
</div>
```

This is the project's only established error-message pattern. Match it exactly rather than inventing a fourth one. Its `py-2.5` is inherited and permitted — the block is **not interactive**, so the 44px rule does not apply.

### 5. Registration degraded state (Surface 3)

When `termoVigente()` returns `null`, `app/registro/page.tsx` renders the **same card shell** (background, gradient bar, logo tile, `Crie sua loja` heading and subtitle — all unchanged) and, in place of `<RegisterForm />`, a single `InlineError` carrying copy **E4**.

**No form fields, no submit button, no disclosure.** A form that renders but cannot succeed is worse than an honest stop. This state is unreachable in any environment that ran the v1 migration; it exists so that a database in an unexpected state produces a legible screen instead of a crash or a silently broken submit.

## Accessibility

- **One `<h1>` per surface.** Gate: `Termos de Uso`. Registro: the existing `Crie sua loja` (unchanged). The gate has no nav landmark, by design.
- **Both terms containers are keyboard-reachable scroll regions:** `role="region"` + `aria-label="Texto dos Termos de Uso"` + `tabindex="0"`. Without `tabindex`, a scrollable box with no focusable children cannot be scrolled by keyboard at all.
- **The checkbox is inside its `<label>`**, so the entire 45px row is the hit area; no `htmlFor`/`id` pairing needed, and none of the existing `htmlFor` associations in `register-form.tsx` are disturbed.
- **Native `required` validation only** on the checkbox — the browser announces it and focuses it. Do not intercept with `preventDefault` and a custom message; the server-side E3 string covers the JS-disabled path.
- Every button is a real `<button type="submit">` inside a `<form action={...}>` — no `<div onClick>`, consistent with the project's zero-`fetch` Server Action model.
- Minimum touch target 44×44px on every interactive control (table in §Spacing Scale).
- **Colour is never the sole carrier of meaning:** the error block pairs red with a full sentence and a glyph; the gate tile pairs slate with the heading `Termos de Uso`; the checkbox state is native and announced.
- **Contrast:** `slate-700` on `slate-50` ≈ 10.9:1; `slate-600` on `slate-50/60` ≈ 7.5:1; `slate-500` on white ≈ 4.8:1; `red-600` on `red-50` ≈ 5.6:1; white on `slate-800` ≈ 13:1. All ≥ 4.5:1. The tenant-coloured accept button carries the pre-existing, out-of-scope contrast risk documented in §Color.
- `<details>` is announced natively as a disclosure by every current screen reader; the summary text states both the action and the version.
