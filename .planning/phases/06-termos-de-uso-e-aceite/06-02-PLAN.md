Metodo `publicar(data: { conteudo: string; publicadoPorId: string })`: le a maior versao com
`prisma.termoDeUso.findFirst({ orderBy: { versao: "desc" }, select: { versao: true } })`, e cria com

projetando `select: { id: true, versao: true, publicadoEm: true }`. O `try/catch` em volta do
`create` mapeia `Prisma.PrismaClientKnownRequestError` com `error.code === "P2002"` para
`new HttpError("Outra publicacao ocorreu em paralelo. Tente novamente.", 409)`, e re-lanca qualquer
outro erro. O comentario nesse catch precisa dizer o porque, nao o que: duas publicacoes concorrentes
leram o mesmo maximo de versao; a constraint unica e a defesa correta e um `findFirst` antes do
insert perde a corrida — o mesmo argumento ja escrito no schema para `EventoWebhookAsaas.eventoId`.

Metodo `registrarAceite(usuarioId: string, termoId: string)`: `prisma.$transaction` interativa com
duas escritas na ordem fato-primeiro-bookkeeping-depois — `tx.aceiteTermo.create({ data: { usuarioId,
termoId } })` e em seguida `tx.usuario.update({ where: { id: usuarioId }, data: { termoAceitoId:
termoId } })`. O `try/catch` em volta da transacao trata P2002 como SUCESSO (retorno silencioso, sem
lancar): duplo clique, retry de rede e reenvio de formulario colidem na constraint e o estado
desejado ja esta no banco. Qualquer outro erro e propagado.
