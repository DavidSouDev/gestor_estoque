<objective>
Fechar o mass assignment de `empresaService.update` **antes ou junto** de as colunas de billing
existirem, para que BILL-04 ("acesso vitalício só via banco, sem UI") não nasça já contornável.

Purpose: hoje `app/api/empresas/[id]/route.ts:83-85` faz `const body = await request.json()` e
repassa o objeto cru para `empresaService.update(id, body)`, que repassa cru para
`prisma.empresa.update({ data })`. `UpdateEmpresaDTO` é uma `interface` TypeScript — apagada na
compilação, não filtra nada em runtime. No instante em que `acessoVitalicio` existir na tabela,
qualquer ADMIN autenticado consegue `PATCH /api/empresas/<seu-proprio-id>` com
`{"acessoVitalicio": true}` e nunca mais pagar. O check existente `id !== auth.empresaId`
**não protege**, porque o ataque é sobre a própria empresa do atacante.
ASVS V4 (Broken Access Control), classificado como crítico em `02-RESEARCH.md` § Security Domain.

Este plano roda na Wave 1, em paralelo com o plano 01 (que cria as colunas), justamente para que a
janela de vulnerabilidade nunca exista dentro da fase. O allowlist é uma lista **positiva** — não
menciona os campos de billing — então funciona independentemente da ordem em que os dois planos
terminam.

Output: `empresaService.update` reescrito no mesmo estilo campo-a-campo que o `create` do mesmo
arquivo já usa, mais dois testes de regressão que travam o buraco fechado.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| cliente HTTP → `PATCH /api/empresas/[id]` | `await request.json()` produz um objeto arbitrário controlado pelo atacante; nenhuma validação de schema em runtime existe no projeto |
| Server Action `marca/actions.ts` → `empresaService.update` | Payload montado no servidor a partir de `FormData`; confiável quanto às chaves, mas passa pelo mesmo método |
| `empresaService.update` → `prisma.empresa.update` | Fronteira onde um objeto não confiável vira SQL de UPDATE |
