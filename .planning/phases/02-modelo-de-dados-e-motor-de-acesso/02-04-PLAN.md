<objective>
Construir o mecanismo de escrita da trilha de auditoria (BILL-05): um serviço que grava **uma**
linha por transição real, de forma idempotente sob concorrência, e um agendador que tira essa escrita
do caminho do response.

Purpose: `avaliarAcesso` vai rodar dentro de `revalidarConta` (plano 02-06), ou seja **a cada request
autenticado**. D-16 exige gravar auditoria só na transição real; sem isso, cada page view do admin
geraria uma linha. E uma escrita no banco dentro do render de layouts/pages bloquearia o TTFB de
toda tela do admin e rodaria mesmo com o render abortado. As três peças que resolvem isso —
`after()`, compare-and-swap e `React.cache()` — estão descritas em `02-RESEARCH.md` Pattern 3.

Output: `lib/agendar-pos-resposta.ts` (sem analog no repositório — nenhum trabalho pós-resposta existe
hoje) e `app/services/acesso.service.ts` (novo service, classe + singleton como todos os outros).

Decisão de discrição exercida aqui (CONTEXT §Claude's Discretion): o efeito colateral de escrever a
auditoria mora num **método de serviço** (`acessoService.registrarTransicao`), não dentro de
`avaliarAcesso` — a função pura continua pura, e a comparação com o estado anterior é responsabilidade
de quem chama.

Escopo negativo explícito: **não** criar nenhum endpoint de leitura de auditoria nesta fase
(`02-RESEARCH.md` § Security Domain V4: "nenhum endpoint de leitura de auditoria é criado nesta fase —
mantenha assim"). **Não** auditar a ativação de `acessoVitalicio` (D-15 aceita a limitação; trigger de
banco e diff periódico estão em Deferred Ideas). **Não** plugar nada em `revalidarConta` aqui — isso
é o plano 02-06.
</objective>

Método `async registrarTransicao(params: { empresaId: string; anterior: StatusAcesso | null;
novo: StatusAcesso; causa: CausaTransicaoAcesso })`:

1. **D-16, guarda barata:** se `params.anterior === params.novo`, `return null` imediatamente, sem
   tocar o banco. Esta é a guarda que impede uma linha por request — `avaliarAcesso` roda a cada
   request autenticado.
2. Abrir `prisma.$transaction(async (tx) => { ... })` (transação interativa; dentro do callback usar
   sempre `tx.`).
3. **Compare-and-swap:** `const { count } = await tx.empresa.updateMany({ where: { id: params.empresaId,
   ultimoStatusAuditado: params.anterior }, data: { ultimoStatusAuditado: params.novo } });`
   O `where` casa o valor **esperado** do status anterior — inclusive `null`, que no Prisma é
   igualdade a NULL válida e é o caso do primeiro registro pós-`REGISTRO`/`BACKFILL`.
4. Se `count === 0`, `return null` — outro request concorrente já registrou esta transição. No-op sem
   exceção e sem constraint única artificial.
5. Se `count === 1`, `return tx.auditoriaAcesso.create({ data: { empresaId, statusAnterior: anterior,
   statusNovo: novo, causa } });` — exatamente 4 campos no `data`, mais nada. `createdAt` vem do
   `@default(now())` do schema. **D-17 proíbe** snapshot dos fatos de billing na linha de auditoria.

JSDoc do método explicando por que o `updateMany` condicional é o compare-and-swap: dois requests
concorrentes do mesmo admin (ex.: uma page e uma Server Action) observam a mesma transição e
agendariam dois efeitos; condicionar o `create` a `count === 1` faz o segundo virar no-op.
Um read-then-write (`findFirst` da última linha + `if` + `create`) não é atômico e gravaria duas
linhas idênticas.

Este service não valida entrada de usuário e não lança `HttpError`. Não adicionar nenhum método de
leitura de auditoria — nenhum endpoint de leitura existe nesta fase, por decisão de segurança.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| requests concorrentes do mesmo admin → escrita de auditoria | Uma page e uma Server Action são requests HTTP separados; ambos podem observar a mesma transição no mesmo instante |
| efeito pós-resposta → ciclo de vida do processo | O trabalho agendado roda fora do request; uma exceção lá não tem quem a trate |
| contexto de execução (request Next vs. Vitest vs. worker) → `after()` | `after` depende do `AsyncLocalStorage` que só existe durante um request do Next |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-15 | Repudiation | Race na escrita de auditoria gerando linhas duplicadas e poluindo a trilha | mitigate | Compare-and-swap `tx.empresa.updateMany({ where: { id, ultimoStatusAuditado: anterior } })` + `create` condicionado a `count === 1`, dentro de `$transaction`; caso de teste com `count: 0` |
| T-02-16 | Repudiation | Falha silenciosa da auditoria (promise solta, log perdido) | mitigate | `.catch` obrigatório dentro de `agendarPosResposta` com `console.error("[acesso] ...")`; a Fase 5 (worker, WRK-01) reconcilia o que se perder |
| T-02-17 | Denial of Service | Escrita no banco dentro do render, disparada por um GET, bloqueando o TTFB de toda tela do admin | mitigate | `after()` do `next/server` tira o efeito do caminho do response (uso literal descrito na doc empacotada do Next) |
| T-02-18 | Denial of Service | Uma linha de auditoria por request autenticado inflando a tabela | mitigate | Guarda `anterior === novo` antes de qualquer I/O (D-16) + `React.cache()` de `revalidarConta` deduplicando por request |

| T-02-SC | Tampering | npm installs | n/a | Nenhum pacote novo nesta fase (`02-RESEARCH.md` § Package Legitimacy Audit) |
