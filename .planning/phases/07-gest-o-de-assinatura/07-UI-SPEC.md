# Phase 7 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope of this contract:** four UI surfaces — (1) the new subscription screen at `/[slug]/admin/assinatura` with its five states, (2) the cancellation confirmation view that replaces it, (3) two navigation entry points (`admin-nav.tsx` for COMPLETO, `simples-top-bar.tsx` for SIMPLES), (4) the post-checkout poller mounted on the existing blocked screen and on State A of the subscription screen. Everything else in Phase 7 is service, client and gateway work with no visual output.

**Prime directive:** this phase introduces **zero** new visual language. Every surface is assembled from markup already in this repository: the `bloqueado-card.tsx` card shell, the `AvisoCarencia` amber strip, the single `InlineError` block used by `login-form.tsx` / `register-form.tsx` / `bloqueado-card.tsx`, the `PagarButton` CTA, the `ConfirmarRemocao` view-replacement confirmation, the `StatCard` value block from the dashboard, and the `admin-nav.tsx` item row. Every token below was extracted from existing code, not invented.

**This is the phase that spends Phase 4's colour budget on purpose.** Phase 4 taught one association — amber = your payment situation — and Phase 6 deliberately refused to reuse it for a non-payment event. Phase 7 is squarely inside that vocabulary, so amber returns here, but only on the one state that is genuinely a payment problem (carência). Cancellation is **not** painted amber or red: it is a choice the product offers, not a failure. See §Color.

### Confirmation form factor — D-03 says "modal"; this contract implements it as a view replacement

D-03 locks: *"Cancelar exige uma **confirmação explícita via modal**, mostrando a **data exata** … antes do segundo clique."* `07-RESEARCH.md` §A6 assumed an in-page overlay.

**Decision (confirmed with the operator this session): the confirmation is a view replacement, not an overlay.** D-03's substance — explicit confirmation, two clicks, exact date visible before the second — is delivered in full. Only the mechanism differs.

| Why | Evidence |
|-----|----------|
| The project has **zero** overlays | `grep -rn "<dialog\|role=\"dialog\"\|aria-modal\|createPortal\|fixed inset-0" app/ --include=*.tsx` returns **zero hits**, verified this session. Phase 6 found the same and recorded it. |
| The project already has this exact confirmation | `app/[slug]/admin/(protected)/_components/simples/confirmar-remocao.tsx` — the component is **returned in place of** the previous view by `combo-hub.tsx:93-95`, `produto-hub.tsx`, `promocao-hub.tsx`. It is not an overlay and never was. |
| An overlay is a system, not a component | Focus trap, scroll lock, `Escape`, return-focus, portal, `aria-modal`, background inert. Establishing all of it to confirm one action is inventing a design system inside a phase forbidden from inventing one — the same argument Phase 6 accepted, and `07-RESEARCH.md` §Don't Hand-Roll repeats it verbatim ("Modal de confirmação → `useState` + markup, como `confirmar-remocao.tsx`"). |
| Milestone consistency | Phase 6 deferred the modal primitive to milestone level. Building one in Phase 7 would mean the product's only overlay exists on exactly one screen. |

**The pattern is adopted; the tokens are normalized.** `ConfirmarRemocao` is written in the SIMPLES idiom — `text-5xl` emoji, `text-2xl`/`text-3xl` heading, `px-8 py-4 text-lg` buttons — sized for the simplified interface. The cancellation view uses the **card-scale tokens of `bloqueado-card.tsx`** instead (`text-xl/[1.2]` heading, `py-3 text-sm` buttons). This is the same "adopt the pattern, normalize the tokens" move Phase 6 made when it took `collapsible-section.tsx`'s `<details>` but overrode `py-2.5` → `py-3` and `font-medium` → `font-semibold`. **`confirmar-remocao.tsx` itself is not edited.**

**No emoji.** `ConfirmarRemocao` opens with a `🗑️` text node. Every billing surface built in Phases 4 and 6 uses inline SVG. The cancellation view uses inline SVG or no glyph at all — it does not introduce the first emoji into the billing language.

## Typography

Four sizes, two weights. Line heights are declared as ratios and implemented with Tailwind 4's line-height modifier (`text-sm/[1.5]`).

| Role | Size | Weight | Line Height | Tailwind | Where |
|------|------|--------|-------------|----------|-------|
| Meta | 12px | 400 or 600 | 1.33 | `text-xs` / `text-xs font-semibold` | Field labels (`ACESSO ATÉ`, `PRÓXIMA COBRANÇA`); status-pill text; `InlineError` text; poller notice |
| Body | 14px | 400 | 1.5 | `text-sm/[1.5]` | All explanatory copy; card subtitle; confirmation body; nav labels |
| Heading | 20px | 600 | 1.2 | `text-xl/[1.2]` | Page `<h1>` (`Assinatura`); confirmation view `<h1>` |
| Display | 24px | 600 | 1.2 | `text-2xl/[1.2] font-semibold` | The one hero value: the access-until date |

**Button labels** are `text-sm font-semibold` (14px / 600) — matching `PagarButton`, `login-form.tsx:71` and `bloqueado-card.tsx:106` exactly.

### Binding rule: exactly one Display value on the screen

`acesso até {data}` is the single most important fact on this surface — it is the answer to the question that brings a user here, and it is the number D-03 requires be unmissable before a cancellation is confirmed. It gets 24px/600 and **nothing else on the screen does.** `PRÓXIMA COBRANÇA` — which comes from the gateway and can be unavailable (State D) — renders at Body size. Giving a field that may be missing the same weight as a field that never is would make the degraded state look broken rather than partial.

**Legacy carve-outs (three, documented, none edited by this phase):**
- `admin-nav.tsx:104` uses `font-medium` (500) on nav rows. The new `Assinatura` row **matches its siblings** for the same reason it matches their padding. This is the only weight-500 permitted in this phase.
- `StatCard` in `(protected)/page.tsx:31` uses `text-2xl font-bold` (700). The Display role here is `font-semibold` (600), not 700 — the pattern is borrowed, the weight is normalized.
- `confirmar-remocao.tsx` uses `font-bold` at `text-2xl`/`text-3xl`. Not edited, not matched.

**No new markup in this phase may use weight 700.** Weight 500 is permitted **only** on the appended `AdminNav` row.

**Rationale for 400+600:** the codebase histogram is `font-semibold` 126 × `font-bold` 45 × `font-medium` 28 — semibold is the established emphasis weight, and `bloqueado-card.tsx` / `aviso-carencia.tsx` (the two billing surfaces already shipped) use 600 exclusively.

### Accent reserved for — explicit list

Tenant `primaryColor` may be applied to **exactly these three things** in this phase:

1. The `background` of the `PagarButton` on the subscription screen (`Assinar agora` / `Reativar assinatura`), via the existing `bloqueado` variant.
2. The `--tw-ring-color` focus ring of that same button.
3. The `background` of the active `Assinatura` nav row in `AdminNav` — automatic, produced by the existing `style={active ? { backgroundColor: primaryColor } : {}}` on line 108. **No new code applies it.**

**Accent is explicitly NOT used for:** the `Cancelar assinatura` trigger, either confirmation button, the status pill in any state, the field tiles, the card border, body text, the `SimplesTopBar` icon button, or the poller strip.

### Why cancellation is the only red, and only at the second click

Cancelling is a **destructive** action — it stops future billing and starts a countdown to losing the panel and the catalogue — so the confirm button gets `red-600`, matching `confirmar-remocao.tsx:34` exactly. That is the project's one established destructive treatment.

But the **trigger** on the main card is not red. It is a quiet ghost button (`text-slate-500`, `hover:bg-red-50 hover:text-red-600`) — the exact hover treatment already on the logout rows in `admin-nav.tsx:120` and `simples-top-bar.tsx:47`. Painting the resting state red would make a legitimate, product-sanctioned choice look like a hazard on a screen the user opened to check a date. Red arrives at the moment of consequence and not before.

### Why the cancelled state is slate, not amber and not red

A cancelled-but-still-paid company is **not** in trouble. `avaliarAcesso` D-06 keeps it `EM_DIA`; nothing is overdue; the panel and catalogue are fully live; access continues to a date we can state exactly. Amber would tell the user their payment needs attention when it does not, and would collide with the genuine carência signal for a user who later enters one. Red would shame a user for taking an option the product advertises. Slate reads as procedural, which is what it is. The *information* — the end date and the fact of non-renewal — carries the weight, not the colour.

### Why State D (gateway unavailable) does not turn the screen red

D-02b requires a clear degraded state that neither freezes the page nor presents stale data as current. The card is therefore split into two data zones (see §Component Contracts → 1):

- **Zone 1 — local facts.** Status and access-until, derived from `avaliarAcesso` over the company's own columns. **Never unavailable.** Renders identically in State D.
- **Zone 2 — gateway facts.** Next charge and cycle, from the live Asaas read. **Only this degrades.**

So State D shows a normal, correct, fully-coloured Zone 1 and a single `InlineError` where Zone 2 would be. The user's account is not broken and the screen must not imply it is. The error copy says so explicitly. **Do not grey out, disable or hide Zone 1 in State D**, and **do not disable the `Cancelar assinatura` button** — a failing read does not imply a failing write, and pre-disabling it would deny a user the action on the exact screen that exists to provide it.

**Inherited contrast risk (out of scope, do not "fix" here):** a tenant that picks a pale `primaryColor` already gets white-on-pale text on the login button, the blocked-screen button and the active nav row today. The subscription screen reproduces that existing pattern. Validating tenant colour contrast is a separate concern with a separate blast radius.

### The abort button says `Manter assinatura`, never `Cancelar`

`confirmar-remocao.tsx:40` labels its abort button `Cancelar`. **That label must not be reused here.** On a dialog whose subject is a cancellation, a button labelled `Cancelar` is genuinely ambiguous — it reads equally as "cancel the subscription" and "cancel this dialog", and the two mean opposite things. A user who misreads it either cancels a subscription they meant to keep or fails to cancel one they meant to end, and both outcomes end in a support ticket or a chargeback, which is the exact failure D-03 exists to prevent. `Manter assinatura` states the outcome of pressing it and cannot be misread.

### Locked block: cancellation confirmation copy (D-03)

Heading (`<h1>`): **`Cancelar a assinatura?`**

Body, one paragraph, **verbatim**:

> **`Seu acesso continua ativo até {data} e a assinatura não será renovada. Depois disso, o painel e o catálogo da sua loja saem do ar.`**

D-03 requires the exact date be visible *before* the second click, and `FEATURES.md` records that without this sentence users open tickets or file chargebacks. Three binding properties:

1. **`{data}` is the last day of access, formatted `dd/mm/aaaa` in `America/Sao_Paulo`.** See §The date rule below — this is not `acessoAte` printed directly.
2. **The second sentence is byte-identical to `aviso-carencia.tsx`'s** (`"Depois disso, o painel e o catálogo da sua loja saem do ar."`). The user has likely already read that exact sentence in the grace banner. Reusing it means the consequence of cancelling and the consequence of not paying are described identically, because they *are* identical (D-06: `CANCELADO` is treated as `BLOQUEADO`). Two paraphrases of one fact is two things to keep true.
3. **No `{data}` means no confirmation view.** If `acessoEfetivoAte` returns `null` the button must not render — see §Component Contracts → 3. A confirmation dialog that cannot state the date fails D-03 outright.

### The date rule — display the last day, not the stored bound

**This is the single easiest thing to get wrong in this phase, and it is wrong by default.**

`acessoAte` and `trialFim` are **exclusive upper bounds**. `avaliarAcesso` compares `agora < fatos.acessoAte` (`lib/avaliar-acesso.ts:76`), and `acessoAteAposPagamento` documents itself as *"o LIMITE SUPERIOR EXCLUSIVO consumido por `avaliarAcesso`"* (`lib/billing/asaas/datas.ts`). Both hold **midnight São Paulo of the day after the last day of access**.

Rendering that value directly produces an off-by-one that is invisible in code review and visible to every user: a company whose access ends the instant 15/10 begins would be told **`ativo até 15/10`**, on a day it has nothing. Independently, `lib/format.ts:formatDate` passes **no `timeZone`**, so on any server not set to São Paulo the same value drifts another calendar day.

**Binding rule — both halves are required:**

1. The displayed date is the **last day of access** = `acessoEfetivoAte(fatos)` minus one day, resolved on the São Paulo wall clock.
2. It is derived by a **pure function in `lib/`, colocated with `acessoEfetivoAte`**, taking the instant by parameter. **Never inline in a component, never in the page, never a second copy.**
3. It is formatted `dd/mm/aaaa` with `timeZone: "America/Sao_Paulo"` explicitly set.

This is the same discipline `lib/avaliar-acesso.ts` already declares for `diasRestantesDeCarencia` ("o ÚNICO lugar autorizado a calcular dias restantes") and that `07-RESEARCH.md` §Anti-Patterns restates: *"Recalcular 'dias restantes' ou 'acesso até' na UI"* is forbidden. `lib/fuso-sao-paulo.ts` carries an explicit **do-not-re-derive** warning and must be the only source of São Paulo wall-clock arithmetic — the helper composes it, it does not reimplement it.

**Warning signs:** `formatDate(acessoAte)` anywhere; any `- 86400000` or `setDate(-1)` outside `lib/`; a `new Date()` inside any component in this phase; `Intl.DateTimeFormat` constructed in a component; a test that only covers `EM_DIA` and never a date whose São Paulo day differs from its UTC day.

### Surface 3b is not optional — SUB-02 is false without it

`admin-nav.tsx` renders **only** for `modoInterface === "COMPLETO"` (`(protected)/layout.tsx`). SIMPLES tenants get `SimplesTopBar`, which offers exactly two destinations: a gear to `/marca` and a logout button. D-06 names only `admin-nav.tsx`, so as literally specified **a SIMPLES tenant would have no route to `/assinatura` at all** — SUB-02 ("usuário pode cancelar a assinatura") would be false for that entire population, and the phase goal "cancela sem falar com ninguém" would be false with it.

Confirmed with the operator this session: **add the entry point to `SimplesTopBar` as well**, as an icon `<Link>` beside the gear, using the identical `h-10 w-10 rounded-xl text-slate-400 hover:bg-slate-100 hover:text-slate-600` treatment and a `title="Assinatura"`. This is the minimum change that makes the requirement true for every tenant.

**Placement in `SimplesTopBar`:** between the gear and the logout button. Logout stays last — it is the one control whose position users have memorized and the only one with a red hover.

**Placement in `AdminNav`:** last in `buildNavItems`, after `Minha Loja`. The existing six are ordered by daily frequency (Início → Produtos → Combos → Promoções → Estoque → Minha Loja); subscription is the least-frequently-visited destination in the product and belongs at the end of that gradient, adjacent to the account-level controls.

### Reachability is bounded, and that is by design

`07-RESEARCH.md` §Pitfall 5: `/assinatura` lives inside `(protected)`, which `requireAdminSession` closes via `acessoBloqueado`. A `BLOQUEADO` or expired-`CANCELADO` company clicking `Assinatura` is redirected to `/bloqueado`, and the nav is not rendered for it at all.

**This is correct and must not be "fixed".** For a company that has lost access, the canonical screen is `/bloqueado` — it already carries the pay button (Phase 4) and now carries the poller. `/assinatura` serves TRIAL, EM_DIA, CARENCIA, VITALICIO and cancelled-with-residual, which is precisely the audience of success criteria #1 and #3. **Any plan that moves `/assinatura` outside `(protected)` reintroduces the `ERR_TOO_MANY_REDIRECTS` class documented in `lib/session.ts` and in the header of `bloqueado/page.tsx`.** Any E2E that expects to reach `/assinatura` as a blocked company is asserting a bug.

### 1. `AssinaturaCard` — the five states

**Props (server-computed; the component makes no decisions and reads no clock):**

```ts

  rotuloStatus: string;                  // pill text, resolved on the server
  tomStatus: "positivo" | "atencao" | "neutro";  // pill ramp, resolved on the server
  ultimoDiaDeAcesso: string | null;      // ALREADY formatted "dd/mm/aaaa" in America/Sao_Paulo
  precoMensal: string;                   // ALREADY formatted via formatCurrency → "R$ 29,90"
  gateway: { proximaCobranca: string | null; ciclo: string | null; disponivel: boolean };
  podeCancelar: boolean;
  podePagar: boolean;
  erroCheckout: boolean;                 // E3

  cancelarAction: () => Promise<{ error?: string }>;

Same discipline as `BloqueadoCard` and `AvisoCarencia`: **props are decisions already taken, not raw state.** The component contains no `new Date()`, no `Intl` constructor, no status comparison, no `avaliarAcesso` call and no branch on `canceladoEm`. `07-RESEARCH.md` §Pattern 3 assigns all five branches to `page.tsx`, in a normative order.

**The five states, in the order `page.tsx` must evaluate them** (inverting the order makes the product call Asaas with a removed subscription id):

| 2 | `canceladoEm !== null` | C — cancelled | `Cancelada` · neutro | **No** | hidden | `Reativar assinatura` |
| 3 | `asaasSubscriptionId === null` | A — empty | `Sem assinatura` · neutro | **No** | hidden | `Assinar agora` |

Client component. One `useState` for the view, one `useTransition` for the action — the exact idiom of `combo-hub.tsx:100-120`, which `07-RESEARCH.md` §Pattern 2 cites as the literal precedent.

**Trigger (default view):**

```

```

**Confirmation (replaces the card body, does not overlay it):**

```

  <p class="mx-auto mt-2 max-w-md text-sm/[1.5] text-slate-500">

**Binding rules:**
- **The component receives `ultimoDiaDeAcesso` as a required, non-null string.** If the page cannot produce a date, it must not render this component at all (`podeCancelar: false`). D-03 is unsatisfiable without the date; a confirmation reading "ativo até —" is worse than no button.
- **`cancelarAction` takes no id.** D-05 and `07-RESEARCH.md` §Pitfall 11: the Server Action's only parameter is `slug`, and the subscription id is derived from `session.empresaId` on the server. **No hidden input, no prop, no argument carrying `assinaturaId`, `subscriptionId` or `customerId` may exist in this markup.** This is a grep-checkable rule and a candidate `gates:fase-07` invariant.
- On success: `router.refresh()`, then return to the default view. The page re-renders in State C. Do **not** hand-render an optimistic "cancelada" state — the local write is the only thing that makes it true, and `07-RESEARCH.md` §Pitfall 1 names the optimistic variant as the worst available outcome.
- On failure: stay in the confirmation view and render the error **in place**. Never close the view on failure — that reads as success.
- `pending` disables **both** buttons. A user who presses `Manter assinatura` mid-flight would otherwise see the view close while a cancellation completes behind it.
- **No `Escape` handler, no focus trap, no scroll lock, no `role="dialog"`, no portal.** This is a view, not an overlay. Adding any of them starts building the primitive this contract declined.
- The destructive button is `type="button"` with `onClick`, not a form submit — `combo-hub.tsx` calls the Server Action inside `startTransition` and needs the returned error string. Consistent with the project's zero-`fetch` model: the network call is still a Server Action.

### 5. `PollerDeStatus` — post-checkout convergence (D-01)

Client component. `setTimeout` + Server Action + `router.refresh()`, per `07-RESEARCH.md` §Code Examples #4.

**Backoff (Claude's Discretion under D-01, decided here):** `[2000, 3000, 4000, 6000, 8000, 10000, 12000]` ms — 7 attempts over ~45 s. Converges in seconds, has a finite ceiling, and its total is short enough to sit inside a user's attention span while returning from a checkout.

**Binding rules:**
- **The Server Action reads LOCAL facts only.** It calls `revalidarConta` → `avaliarAcesso`. **`asaasClient` must not be imported by it** — `07-RESEARCH.md` §Pitfall 3: 7 attempts × every returning payer against a 25 000-request/12 h quota, to answer a question the gateway cannot answer anyway. What the user is waiting on is whether the *panel unlocked*, which is decided locally. Grep-checkable; candidate `gates:fase-07` invariant.
- **`clearTimeout` on unmount is mandatory**, not defensive. Without it a navigation leaves a live timer calling a Server Action against an unmounted tree.
- **No spinner, no animation, no progress bar.** The strip is a static line of text that changes once, at exhaustion.

**Copy presumes nothing.** The poller mounts on `/bloqueado` for *every* blocked visitor, most of whom did not just pay. Asserting "Confirmando seu pagamento…" to them would be false.

| Phase | Copy | Style |
|-------|------|-------|
| polling | `Verificando o status do seu acesso...` | `text-xs text-slate-500` |
| exhausted (E5) | `Se você acabou de pagar, a confirmação pode levar alguns minutos. Atualize a página em instantes.` | `text-xs text-slate-500` |

Strip container: `mt-4 rounded-xl bg-slate-50 px-4 py-3 text-center`, `role="status"` (polite live region — never `role="alert"`, which would interrupt a screen-reader user every few seconds).

**Mount sites:**
1. `bloqueado-card.tsx` — **unconditionally**, between the body copy and the pay button. Zero change to `successUrl` (`07-RESEARCH.md` §Achado 7, option (a)); resolves via the existing `if (!conta || !acessoBloqueado(...)) redirect('/${slug}/admin')` guard in `bloqueado/page.tsx` once `router.refresh()` fires. This is the money case: a delinquent company that just paid.
2. `AssinaturaCard`, **State A only** — the window in which `PAYMENT_CONFIRMED` has landed but `SUBSCRIPTION_CREATED` has not, so `asaasSubscriptionId` is still null (`07-RESEARCH.md` §Achado 2: this is the normal first minute of every new subscriber, not an edge case).

**This is the only change `bloqueado-card.tsx` receives.** Its heading, body, tile, buttons and copy are Phase 4 contract and stay byte-identical.

## Accessibility

- **One `<h1>` per view.** Default view: `Assinatura`. Confirmation view: `Cancelar a assinatura?` — the confirmation *replaces* the default view, so exactly one `<h1>` is in the document at any moment. This is a structural advantage of the view-replacement choice: an overlay would have left two.
- **Focus management on view swap.** When the confirmation view mounts, move focus to its `<h1>` (`tabIndex={-1}` + `.focus()`); when it unmounts, return focus to the `Cancelar assinatura` trigger. Without this, a keyboard user presses a button and focus falls to `<body>`. This is the one behaviour an overlay would have given for free and must therefore be implemented deliberately.
- **The poller strip is `role="status"`** — a polite live region. Never `role="alert"`: it updates on a timer and would interrupt a screen-reader user repeatedly. Same rule `aviso-carencia.tsx` follows.
- **Both nav entries carry an accessible name.** `AdminNav` renders a visible `<span>` when expanded and `title` when collapsed; `SimplesTopBar` is icon-only and `title` is mandatory.
- **Colour is never the sole carrier of meaning.** Every status pill pairs its ramp with a text label *and* a distinct glyph (check / triangle / minus). A user who cannot distinguish emerald from amber reads `Ativa` versus `Pagamento pendente`.
- **Destructive confirmation is reachable and reversible by keyboard**: both buttons are real `<button>` elements in DOM order, confirm before abort.
- Minimum touch target 44×44px on every control on the subscription screen; the two navigation entries are 40px by sibling-consistency mandate (§Spacing Scale).
- **Contrast:** `slate-800` on `slate-50` ≈ 13.8:1; `slate-500` on white ≈ 4.8:1; `emerald-700` on `emerald-50` ≈ 6.4:1; `amber-800` on `amber-50` ≈ 7.9:1; `slate-600` on `slate-100` ≈ 6.9:1; `red-600` on `red-50` ≈ 5.6:1; white on `red-600` ≈ 4.8:1. All ≥ 4.5:1. The tenant-coloured pay button carries the pre-existing, out-of-scope risk documented in §Color.
- **No `dangerouslySetInnerHTML`.** Every value on this screen — dates, currency, gateway strings — renders as a React text node.
